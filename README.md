# weight-space

在小规模上复现 "Sparks of Weight-Space Programming"：让 LLM（DeepSeek）**直接读、写一个小 LSTM 的权重**，不训练、不用梯度，然后和梯度训练出来的同结构模型做对比。

## 任务：Dyck-1 括号匹配
- 输入：由 `(` 和 `)` 组成的串。输出：括号是否合法匹配。
- 难负例：一类是翻转一个括号（左右括号数量不等），另一类是轮转（数量相等，但中途深度变成负数）。只数括号个数的规则约 75%。
- 训练和 LLM 能观察到的串长度都 ≤20。测试分三档：`test_id`（2–20）、`test_long`（40–100）、`test_xlong`（200–500）。**核心问题是长度泛化。**
- 模型：LSTM(hidden=4) → ReLU 头(4) → logit，共 137 个参数。`tests/oracle.py` 里有手工构造的解，在所有长度上 100%，用来证明这个架构能解这个任务。

## 对比方式
| 方法 | 能拿到的信息 |
|---|---|
| 梯度训练 `ws/train.py` | n ∈ {32…8192} 条长度 ≤20 的样本，Adam 优化 10000 步 |
| LLM 从零写 `--mode write` | 架构公式和任务描述，权重从全 0 开始 |
| LLM 修模型 `--mode fix` | 一个训练好的模型，目标是修好它的长度泛化 |

LLM 能用的工具：
- `get_weights` / `set_weights`：免费。
- `evaluate`：练习集准确率和错例，每次消耗 1 次前向预算。
- `trace`：给最多 4 个自选的串（每个 ≤20 字符），返回每一步的门控和状态，每次消耗 1 次前向预算。
- `submit`：提交当前权重。

LLM 不能执行代码，也拿不到梯度，所以无法偷偷自己训练。

## 运行
```powershell
uv sync
uv run python -m tests.oracle                       # 自检
uv run python -m ws.train                           # 梯度基线 -> runs/baselines/
Copy-Item .env.example .env                      # 填入 API key；模型和地址也在这里配置
uv run python -m ws.agent --mode write --budget 0  --repeats 5
uv run python -m ws.agent --mode write --budget 10 --repeats 5
uv run python -m ws.agent --mode fix --init runs/baselines/h4_n512_lr0.003_st10000_s0.json --budget 10 --repeats 5
uv run python -m ws.report                          # 汇总表
```

`ws.agent` 会自动读取项目根目录下的 `.env`。可配置：

```dotenv
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash
```

也可以直接通过环境变量覆盖 `.env` 中的值；命令行参数 `--model` 的优先级最高。
每次 LLM 运行都会保存在 `runs/agent/<id>/`，包含完整对话记录 `transcript.jsonl`、最终权重和评测结果。

梯度修复对照：`uv run python -m ws.finetune`，结果写在 `runs/finetune/`。

## 结果（2026-11-06，deepseek-flash，前向预算 10 次）

### 梯度训练基线
- 长度 ≤20：最好能到 100%（hidden=8）。
- 长度 40–100：只有 0.60–0.80。
- 长度 200–500：只有 0.50–0.65。

结论：梯度训练出来的模型普遍无法长度泛化，加大 hidden、加训练步数也没有改善。

### 修模型
被修的是 3 个 h4 模型，修复前在长度 ≤20 上 100%，在长度 40–100 上平均 0.71。

| 方法 | 能改的参数数 | 长度 2–20 | 长度 40–100 | 长度 200–500 | 完全修好的次数 |
|---|---|---|---|---|---|
| flash | ≤13 | 1.000 | 1.000 | 1.000 | 9/9 |
| flash | ≤6 | 0.885 | 0.750 | 0.727 | 2/9 |
| flash | ≤4 | 0.908 | 0.744 | 0.592 | 1/9 |
| 梯度，只用短串数据（全部参数 / top-k / flash 选中的那些参数） | 4–137 | ≈1.000 | 0.69–0.71 | ≈0.51 | 0/45 |
| 参考：梯度，用长串数据 | 13–137 | 0.80–0.94 | 0.87–0.90 | 0.61–0.68 | — |

"完全修好"的标准：长度 40–100 ≥ 0.99，且长度 200–500 ≥ 0.97。

### 观察
- 上限 13 时，flash 每次都用满 13 个参数，把原模型里漏的计数器改成精确计数器，再加一个"曾经变负"标志，基本上是重建了教科书构造。
- 上限 4–6 时能不能修好，取决于原模型的结构：
  - lr0.003_s1 原本就有一个干净的近似计数器（单元 0），改 4 个参数就修好了：`g0` 的 ±1 增量、`f0` 的 bias、输出头的 1 个权重。
  - 另外两个模型在上限 4–6 下 12 次全部失败。
- flash 会提交比原模型更差的权重（短串准确率降到 0.45–0.75），不会退回到之前更好的版本。
- 只用短串数据时，梯度方法修不好：原模型在短串上的损失已经接近 0，数据里没有任何长度信号。即使直接告诉它 flash 改的是哪 13 个参数也没用。

### 保留最好版本（`ws/keepbest.py`）
按对话记录重放 flash 的每一次权重修改，还原出每一版权重，再选出短串练习集准确率最高的一版（分数相同取最新的）。
- 短串准确率从 0.885–0.908 恢复到 0.999，不会再交出比原模型差的结果。
- 修好的次数不变（上限 6 时 2/9，上限 4 时 1/9）。短串练习集看不到长串上的收益，所以"短串略降、长串大涨"的版本会被淘汰。

### 4–6 个参数的修复方案是否存在（`ws/feasible.py`）
在长度 2–100 的混合数据上做梯度搜索。每个模型、每档上限各 15 个候选：flash 试过的参数位置、梯度 top-k、按单元构造的计数器。这个搜索能看到长串数据，只用来判断"解是否存在"，不算公平对比。

| 模型 | 上限 4 | 上限 6 |
|---|---|---|
| lr0.003_s1（对照组） | 1/15（只有从 flash 的解出发的那个候选） | 4/15 |
| lr0.003_s0 | 0/15 | 0/15 |
| lr0.01_s1 | 0/15 | 0/15 |

- 对照组在上限 6 时能从头搜到解，说明搜索方法有效。
- 对照组在上限 4 时，从头搜索的候选即使看到长串数据也修不好；而 flash 只用短串数据就找到了解。
- 两个失败的模型在 60 个候选里都搜不到修复方案，大概率在 4–6 个参数内修不好，至少明显更难。flash 在这两个模型上的失败，不一定是它的问题。

## 新任务 a2b（2026-11-07）
所有命令加 `--task a2b`，结果在 `runs/a2b/`。

任务：串只含 a 和 b，同时满足两个条件才接受：
1. a 的个数恰好是 b 的 2 倍；
2. 每一个前缀里 a 的个数都不少于 b。

串长都是 3 的倍数；只检查比例的捷径规则约 75%。解这个任务需要两个增量不同的计数器（读到 a 加 1、读到 b 减 1；以及读到 a 加 0.5、读到 b 减 1），再加一个"前缀曾经违反"的标志位。网上没有现成的 LSTM 构造。手写的标准解见 `tests/oracle.py`，所有长度 100%。

| 方法 | 长度 3–18 | 长度 42–99 | 长度 201–498 | 完全修好的次数 |
|---|---|---|---|---|
| 梯度训练，最好的一组（h8，8192 条样本） | 1.000 | 0.70–0.75 | 约 0.52 | — |
| **flash 从零写**（前向预算 10 次） | **1.000** | **1.000** | **1.000** | **5/5** |
| 修复前（3 个 h4 模型） | 0.999 | 0.680 | 0.510 | — |
| flash 修模型，上限 13 个参数 | 0.950 | 0.768 | 0.684 | 1/9 |
| flash 修模型，上限 13 个参数，保留最好版本 | 0.999 | 0.747 | 0.630 | 2/9 |
| **flash 修模型，上限 20 个参数** | **1.000** | **0.973** | **0.946** | **8/9** |
| 梯度修复，只用短串数据（全部参数 / top-k / flash 选中的参数） | ≈1.0 | 0.65–0.71 | 约 0.51 | 0/45 |
| 参考：梯度修复，用长串数据 | 0.70–0.90 | 0.73–0.81 | 0.57–0.61 | 0/18 |

### 观察
- **从零写 5/5 全部成功，而且用了两种不同的机制实现"读到 a 加 0.5"：**
  - 2 次让 tanh 工作在非饱和区：预激活设为 atanh(0.5) = 0.549，tanh 正好输出 0.5。
  - 3 次让输入门半开：输入门预激活为 0，sigmoid(0) = 0.5，而 g 仍然饱和在 ±1。这个方法写标准解时没有想到。

  前向只用了 2–3 次：先推导完整方案，再用 trace 验证一次。
- **修模型比从零写难得多**（上限 13 个参数时 1–2/9）。完整的解大约需要 20 多个非零参数，13 个的额度必须大量复用原模型的结构。
- **成功的修复里有"读懂再改"的直接证据。** 原模型的单元 1 已经学出一个近似比例计数器：读到 a 时 g = −0.725，读到 b 时 g = +0.956。flash 读出它的 g 偏置是 0.074，把"读到 a"的输入权重改成 −0.623，使预激活正好是 −0.549 = atanh(−0.5)；同时把 g 的循环权重清零。改完后读到 a 时 g = −0.4998，读到 b 时 g = +1。
- 梯度修复 63 次全部失败，包括能看到长串数据的参考组。

### 放宽到 20 个参数（137 × 0.15）
- 3 个模型都修好了，9 次里 8 次成功（k=13 时是 1/9）。说明 k=13 失败主要是额度不够，不是读不懂原模型。
- 每次成功都恰好用满 20 个参数（有一次用了 19 个），套路一致：
  - 把一个单元改成精确的 ±1 计数器；
  - 复用原模型已有的近似比例单元，按它原来的 g 偏置去凑 atanh(0.5)（保留偏置、输入权重设为 1.04 或 1.25，或者把偏置清零、输入权重设为 0.549），并把这个单元 g 的循环权重清零；
  - 用一个很大的循环权重（100–1000）接到输入门上，做"前缀曾经违反"的锁存标志。
- 唯一失败的一次是另一种失败模式：10 次前向全都花在 trace 和 evaluate 上，一个参数都没改就提交了。原模型在长度 ≤20 上已经 100%，它观察不到任何错误。
- 第 9 次第一次运行时因为 API 连接错误崩溃，第二次运行卡住，都挪到了 `runs/a2b/agent_crashed/`，第三次运行成功。
